# anatomy-locator

아픈 부위를 **가리키는** 도구. 진단하지 않는다. 자세한 배경과 범위 경계는
[SPEC.md](./SPEC.md) 참조.

## 실행

```bash
pnpm install
pnpm dev
```

- `/` — 지시 도구 (제품)
- `/author.html` — 좌표 저작 도구 (M1). 별도 엔트리라 제품 번들에 섞이지 않는다.

## 배포

`main`에 푸시하면 `.github/workflows/deploy.yml`이 GitHub Pages로 올린다
(`pnpm lint` → `pnpm build` → 업로드). `tsc -b`가 build에 포함되므로 타입 오류는
배포를 막는다.

한 번은 손으로 켜야 한다: **Settings → Pages → Source를 "GitHub Actions"로**.

빌드는 `base: './'`라 저장소 이름이 어디에도 박혀 있지 않다. 프로젝트 사이트
(`/pain-drawing/`), 포크, 커스텀 도메인에서 모두 그대로 동작한다.

`refs/`의 도판은 배포물에 들어가지 않는다 — 어떤 코드도 import하지 않고
`public/`이 아니라 `dist/`에 복사되지 않는다.

## 저작 도구 사용 순서

1. **참조 정합** — 이미지를 올리고 `view.landmarks` 기준점을 차례로 클릭한다.
   2점부터 변환이 잡히고 3점 이상은 최소제곱. 반전 여부는 잔차가 작은 쪽으로
   자동 선택되므로 반대쪽 발 사진도 그대로 쓸 수 있다. rms가 정합 품질이다.
   뷰에 분절이 있으면(무릎) **한 번에 한 분절씩** 맞춘다. 칩이 분절별 rms를
   보여주고, 이미지는 지금 고른 분절의 자리에 놓인다.
2. **도형** — 캔버스 클릭으로 중심선 점 추가, 끌어서 이동, 방향키로 미세 조정
   (Shift 10씩), 폭은 슬라이더. Ctrl+Z로 되돌리기.
   관절을 건너는 리본은 **걸침**을 지정한다. 출발 분절의 자리에서 그리고,
   첫 점이 출발 쪽 부착부·마지막 점이 도착 쪽이다 — 점 순서가 곧 방향이다.
3. **메타데이터** — 이름 3종·조직·층·기시/정지. 조직을 인대나 연골로 바꾸면 폼이
   `attachments` 2칸으로 바뀐다. 근막일 때만 어느 쪽인지 저작자가 고른다
   (족저건막은 방향이 있고 관절낭은 없다).
4. **내보내기** — TS 블록을 `structures.ts` / `placements.ts`에 붙여넣는다.
   출처를 채우면 `fidelity: 'traced'` 블록도 함께 나온다.

## 설계상 지켜야 할 것

- **shape는 path 문자열로 저장하지 않는다.** 중심선 `p` + 폭 `w` 숫자 배열로
  저장하고 `ribbon()`이 렌더 시점에 path를 만든다. 좌표 하나만 손으로 고칠 수 있고
  diff가 읽힌다.
- **정밀도 주장도 StructureInView가 할 수 있다.** 도판이 층별이라 트레이싱도
  층별로 끝난다. placement가 provenance를 생략하면 뷰 값을 상속하고, 적으면 그
  구조만 따로 주장한다. 덕분에 부분 트레이싱이 정직하게 표현된다.
- **조직 종류가 서술 형태를 정한다.** 인대·연골은 `attachments` 2개, 근육·힘줄은
  기시/정지. 섞으면 컴파일되지 않는다. 판별 기준은 조직 이름이 아니라 당기는
  방향의 유무여서, 근막만 양쪽을 허용한다 — 족저건막은 방향이 있고 관절낭은 없다.
  `attachments`가 잇는 것도 뼈로 한정하지 않는다: 반월판은 두 부착부가 모두
  경골이고 슬개하 횡인대는 반월판 둘을 잇는다.
- **depth는 Structure가 아니라 StructureInView의 속성이다.** 같은 구조가 뷰마다
  다른 층에 있을 수 있다. `dorsal-interossei`가 발바닥 L4 ↔ 발등 L3로 갈리는 게
  실제 사례다. 층 번호는 뷰 안에서만 뜻이 있다 — 발등에는 발바닥의 1~4층 같은
  교과서적 체계가 없어서, 같은 번호라도 같은 깊이를 뜻하지 않는다.
  `pcl`은 같은 층 체계 안에서 **보는 방향만으로** 갈린다(앞 L3 ↔ 뒤 L2).
- **`boneRef`도 뷰의 속성이다.** 무릎 뒤 뷰는 앞 뷰 기하를 좌우 반전한 것이지만
  슬개골과 경골조면은 뺐다. 앞에서만 보이는 뼈 표지이기 때문이다.
- **면을 바꾸면 선택과 지시 지점을 버린다.** 발바닥 ↔ 발등은 다른 구조가 놓인
  다른 공간이고 층 수도 다르다(5 vs 4). 좌우 전환은 같은 좌표계라 유지한다.
- **`Structure`는 뷰가 아니라 부위에 속한다.** 그래서 `data/foot/structures.ts`가
  뷰 폴더 밖에 있다. 발바닥·발등이 같은 레코드를 참조한다.
- **비활성 층을 `display:none`으로 끄지 않는다.** `isPointInFill`은 DOM에 있는
  element만 판정한다. 얕은 층은 절단연(점선), 깊은 층은 옅은 채움으로 계속
  그리고 `pointer-events: none`만 건다. `isPointInFill`은 `fill="none"`과
  `pointer-events`에 영향받지 않아 고스트로 그린 층도 후보로 잡힌다.
- **반대쪽은 표시 옵션이 아니라 뷰다.** 좌표가 URL로 나가는 이상 좌우가 상태에
  없으면 `at=`이 두 곳을 가리키게 된다. 반전 뷰는 원본 좌표를 그대로 쓰고
  렌더에서만 뒤집으므로, 정규화 좌표가 한 공간에 남아 좌우 지점 이송이 공짜다.
  대신 독립 트레이싱으로 오해되지 않게 `mirrorOf`가 파생 관계를 남긴다.
- **화면 좌우가 해부학적으로 어느 쪽인지는 뷰가 직접 말한다(`edges`).** `side`
  하나로 유도할 수 없다 — 같은 오른발이라도 발바닥은 무지가 화면 오른쪽,
  발등은 왼쪽이다. 근거는 [refs/README.md](./refs/README.md) "좌우는 어떻게
  판별했나".
- 반환은 단일 정답이 아니라 **후보 목록**이다. 표면 한 점 아래에 4~5개가 겹친다.
- **역방향 조회는 지시 지점을 만들지 않는다.** 이름으로 찾으면 뷰·층을 옮기고
  선택만 한다. 없는 좌표를 지어내면 사용자가 짚지도 않은 곳이 `at=`으로 URL에
  남는다. 대신 면을 건너뛸 때 선택은 들고 간다 — 안 그러면 옮겨간 이유가 사라진다.

## 현재 상태 메모

- **트레이싱 진행 중이다.** 19개 중 13개가 traced다 — 1층 두 외전근(Fig. 443),
  2층 전체(Fig. 444), 3층 전체(Fig. 445), 4층 골간근(Fig. 446·447).
  **남은 6개는 L0 족저건막 3개, L1 단지굴근, L4 비골근장건·후경골건**이다.
  건막과 단지굴근은 443에서 건막이 잘려 기시부가 가려 못 했고, 두 힘줄은
  발바닥을 지나가지만 다른 부위에서 와서 층별 도판에 온전히 안 나온다.
  뷰는 여전히 `fidelity: 'schematic'`이다
  — 윤곽·뼈 참조는 손으로 그린 것이기 때문이다. UI는 이 혼합 상태를 그대로
  말한다(푸터는 "일부만", 구조 상세는 구조별 근거).
- **왼발 뷰는 오른발에서 파생된 것이다.** 좌표를 따로 뜨지 않았고 트레이싱
  상태도 오른발과 같다. 내보내기 블록은 `(mirrored)`로, 푸터는 좌우 차이를
  반영하지 않는다고 말한다.
- **발등 뷰의 기하는 발바닥을 좌우 반전한 것이다**(x' = 310 − x). 같은 발의
  반대 면이라 실루엣·뼈·발가락은 거울상이 맞다. 독립 트레이싱이 아니므로
  발바닥 윤곽의 폭 보정도 그대로 따라온다.
- 발등 구조는 배측골간근만 도판(Fig. 446)에서 왔고 나머지 9개는 모식도다.
  발등을 층별로 벗긴 도판이 아직 없다.
- **무릎은 제품 화면에 안 나온다** (`Region.hidden`). 데이터는 그대로 조립되고
  `?view=knee-anterior`로는 열린다. 이 도구는 눌러서 만져지는 것을 가리키는데
  십자인대·반월판은 위치만 맞고 깊이는 닿지 않는다. `reachable: false`를 항목마다
  붙여도 깊이 레일이라는 장치가 "더 내려가 보라"고 권하는 걸 못 막는다.
  스키마 검증의 증거라서 지우지는 않았다. 판별 기준은 SPEC "부위를 고르는 기준".
- **무릎은 전부 모식도다.** 구조 21개, 배치 앞 13 · 뒤 15를 전부 손으로 찍었고
  뷰가 `schematic`이라 푸터도 그렇게 말한다. 뒤 뷰의 기하는 앞 뷰를 좌우 반전한
  것이고(x' = 320 − x), 관절 **안**의 구조는 좌표까지 반전값이다 — 같은 무릎을
  반대에서 본 것이라 전두면 위치가 거울상이기 때문이다. 표층(햄스트링건·비복근두)과
  후방인대만 새로 찍었다.
- **무릎 도판은 아직 못 구했다.** 이 환경의 egress 정책이 위키미디어·archive.org를
  막는다. 파일을 `refs/`에 넣어주면 바로 트레이싱할 수 있게 **분절 정합은 미리
  만들어 뒀다**(아래).
- **자세가 바뀌는 관절은 분절마다 따로 정합한다.** 관절 내부가 보이는 도판은
  무릎을 굽힌 자세고 뷰는 편 무릎이라 전체를 얹는 상사변환이 없다. 뼈 하나
  안에서는 있으므로 `View.segments`(대퇴골 / 경골·비골)로 나눠 `fitSegmented()`가
  각각 구하고, 관절을 건너는 도형만 `applyAcross()`가 두 변환 사이를 보간한다.
  합성 도판으로 검증했다 — 분절 정합은 오차 1e-13, 단일 정합은 경골 몸통에서
  32.8 어긋난다. **단, 걸친 구조의 중간부는 트레이싱이 아니라 재구성이다.**
  양 끝 부착부만 정확하고, 무릎 인대는 거의 전부 여기 해당한다. 근거와 한계는
  [refs/README.md](./refs/README.md) "2번을 골랐다 — 분절 정합".
- `reachable: false`는 무릎에서 처음 쓰였다 — 십자인대·횡인대·슬와근건·후방인대는
  관절 안이라 지시한 점 아래에 있는 건 맞지만 밖에서 누를 수 없다. 발에서는
  전부 `true`였다. **이건 필드가 검증됐다기보다 그 부위가 안 맞는다는 신호였다.**
- **안쪽 뷰는 통증 위치 때문에 넣었다.** 경골 내측면은 근육이 안 덮어 뼈를 직접
  누르게 되고(내측 경골 스트레스 증후군), 복사뼈 뒤 굴근지대 밑이 족근관이다.
  둘 다 손가락으로 정확히 짚는 자리다. 이 뷰의 L3은 다른 두 면과 달리 깊이가
  아니라 **한 통로에 모인 것들**로 묶인다 — 층 번호가 뷰 안에서만 뜻을 갖는다는
  규칙이 없으면 표현할 수 없다.
- **앞 뷰는 대부분 재사용이다.** 14개 중 6개(신근지대·전경골근건·장지신근건·
  장무지신근건·제3비골근·심비골신경)가 발등 뷰와 같은 레코드다. 앞 칸은 종아리에서
  발등으로 그대로 이어지는 칸이라 그렇게 되는 게 맞다. 심비골신경은 이제
  발등 L3 · 종아리 바깥 L3 · 종아리 앞 L2 — 뷰마다 번호가 다르다.
- **종아리는 전부 모식도다.** 구조 23개를 새로 만들고 배치 112개(좌우 포함)를
  손으로 찍었다. 도판은 없다. 뒤 뷰는 무릎 아래부터 발꿈치까지, 바깥 뷰는
  **뒤 뷰의 반전이 아니라 따로 찍은 면**이다 — 발등이 발바닥의 거울상인 것과
  달리 옆면은 뒤에서 본 면의 거울상이 아니다.
- **부위 경계를 넘는 구조는 레코드를 공유한다.** 비골근장건·후경골건·장지굴근건·
  장무지굴근건·심비골신경은 발에, 비복근 두 갈래는 무릎에 이미 있던 것을 종아리
  placement가 id로 참조한다. 그래서 후경골건이 발바닥 L4이자 종아리 뒤 L3가
  되면서도 레코드는 하나다. 발바닥 도판에서 트레이싱하지 못한 두 힘줄이
  종아리에서는 자리를 얻었다.
